# Architecture

Artificial Realities generates a film as a sequence of short clips while a viewer watches and steers. This document describes the current orchestration, the **Director engine** (`graph: "director"`). It replaced a four-role engine after a 30-turn A/B and a 180-segment run; why it is built the way it is, with the evidence, is in [`decisions.md`](decisions.md).

## Design in one paragraph

Two LLM roles on two clocks, everything else deterministic. The **Director** makes one structured call per **beat**, one action or state of the film that lasts one to a few clips, and returns everything the beat needs: each clip's picture, what is said, what changes in the world in that clip, and how the viewer's input was handled. The engine then emits the beat's clips one per segment with no LLM on the way, and asks the Director again when the beat has played out, or at once when the viewer speaks, dropping the rest of the beat. The **Showrunner** runs off the critical path on triggers (scene boundaries, a compaction interval) and does memory and planning in one call: it compacts the event log into summaries, records durable facts, prunes dead threads, and writes the next scene card; nothing ever waits for it. The authority rule between them: the Director is the only creative call on the critical path, and while a viewer's direction is active it outranks the scene card, whose goal and candidate beats are the menu for the quiet stretches; the Showrunner owns the memory and authors the idle film. Both system prompts state it. Code owns the rest: a typed world model that is the only source of truth, structured where code reads it (kind, presence, location, gone) and prose where only the writers do (each entity's `state`); a validator that decides what the Director may change, clip by clip; a context assembler that decides what goes into the prompt; a prompt compiler that speaks the video model's dialect in as few words as the next clip needs; persistence; and a live loop that renders each clip just in time so a viewer's line reaches the earliest clip that is not yet rendering.

```
viewer input ─▶ Engine (deterministic, asyncio)
                 · keeps every input · just-in-time render · persistence
                     │ assemble context                         │ triggers: scene exit,
                     ▼                                          │ replan flag, every N segments
        Context assembler (code)                                ▼
        bible · scene card · active entities + character   Showrunner (LLM, slow clock)
        state · threads · last K clips · where the         compact log → summaries · cast notes
        picture is · pending interventions                 · prune threads · arc · next scene card
                     │                     ◀── plan + summaries land at the next plan ──
                     ▼                                          ▲ reads log + state
        Director (LLM, once per beat)                           │
        clips (action · end state · ops) · dialogue             │
        · thread ops · viewer disposition · flags               │
                     │ proposes    ◀── reject, re-ask once      │
                     ▼                                          │
        Validator (code): schema · cast registry · entity existence · structural rules, per clip
                     │ apply one clip per segment               │
                     ▼                                          │
        World model (typed, persisted per clip) ───────────────┘
        entities + character state · threads · interventions · plan · event log · summaries
                     │ clip spec
                     ▼
        Prompt compiler (code) ─▶ LTX-2.5 server (sliding window, native audio) ─▶ Player (web / ffplay)
                                                                                    ▲ viewer types here, mid-stream
```

## A beat, then its clips

**Plan** (the Director call, once per beat):

1. **Land.** If a Showrunner task spawned earlier has finished, land its update (summaries, notes, pruned threads, arc, and a new scene card when it replanned). A task still running is left alone and the plan proceeds on the current plan: the fast clock never pays for the slow one. Only the end of a run awaits it.
2. **Record input.** A non-empty viewer line becomes an `Intervention` with disposition `pending`. Nothing is dropped: the live loop joins lines typed together, but every line the engine sees is recorded.
3. **Bootstrap.** On the first segment the Showrunner runs synchronously to write the arc and the opening scene card from the blueprint; nothing is on air yet. This is the only synchronous Showrunner run and the only route by which the blueprint's `opening` reaches the film: the Showrunner's system prompt carries it ("How the film opens"), and the Director's does not. It costs a few seconds during the lead build, before anything is on air, which is why it stays synchronous. The arc it writes orients both roles (the Showrunner keeps it current with its act marker; the Director reads it next to the scene card); the code enforces nothing from it.
4. **No pacing gate.** No code measures whether the film is moving or ends a scene: the plan shows both roles how long the scene has run against `scene_seconds`, the Director's rules ask it to end a bit that keeps coming round, and the Showrunner judges the scene on every compaction pass. Code that measured stagnation once reported no pacing pressure on every beat of a ball-passing loop, because each hand-off counted as a change, and the Showrunner deferred to it instead of the loop it could read.
5. **Director call.** The context assembler renders the bible (static, cache-friendly system prompt: the film block, the truths, the picture and where the first clip starts, cast sheets with their looks and voices, locations), then in the user prompt the plan, the world now (with each character's `now` line and the Showrunner's notes), open threads, the viewer section, summaries, the recent clips verbatim with the beat each belongs to, and where the picture is (how the previous beat ended, in full or cut short, and the image the last rendered clip ends on). The Director returns a `BeatPlan`: an intent, a framing, one to `max_clips_per_beat` clips each with one or two sentences of action, an end state, camera motion, sound, who is on screen, dialogue and the entity ops that happen in that clip; plus thread ops, the viewer disposition and the flags. The system prompt is about 2.8K tokens and cached; input size is not the latency term (output tokens are), so nothing is cut from it for latency. The opening scene's summary is pinned in the summaries section as the first compaction window, since the start of a film is what viewers refer back to. While a viewer's direction is active (the beat answers a line, or the last absorbed line is younger than `viewer_momentum_seconds`, 90 s of film, and no newer line replaced it) the viewer section carries it and the plan section pauses the scene card (its goal and candidate beats), which returns whole when the direction expires; the Showrunner always sees its own card. A new card clears the direction only if its run's trigger arose after the line: the replan a line provokes, spawned at once or held by the gap and spawned later, does not erase that line.
6. **Validate.** Hard violations anywhere in the beat (an unknown entity, a new character the story's cast does not allow or one without a description of how it looks, a second copy of the protagonist or its removal, a perspective the story does not permit, a line from someone who is not a character) trigger exactly one re-ask with the violations spelled out. The beat is then held by the engine; nothing has been applied yet.
7. **Trigger.** `scene_done` or `needs_replan` → Showrunner in replan mode; `compaction_interval` segments since the last compaction → compact mode, in which the Showrunner judges whether the scene is still developing or going in circles and replans if it is stalled or spent. At most one run is in flight and runs are at least `showrunner_min_gap` segments apart; a trigger inside the gap or with a run in flight is noted and looked at again at the next plan, and a `scene_done` or `needs_replan` flag is remembered (`_held_trigger`) and raised again at every plan until a replan run takes it or a new card lands. The run is not spawned here: it is spawned at step 10 of the beat's first clip, after that clip is applied and logged, so its snapshot and its compaction window (`..at_segment`, inclusive) contain the clip that caused it; a beat cut before its first clip spawns nothing and the next plan decides again. The task lands at step 1 of the first later plan that finds it finished.

**Emit** (one clip per segment, no LLM):

8. **Apply.** `apply_clip` mutates the world with that clip's ops (entity introduce/update/remove, an entity's `state` replaced whole, presence from the clip's `on_screen`), and on the beat's first clip also lands the thread ops and the intervention disposition. Unresolvable ops are dropped and logged as warnings, never silently. Because ops ride on the clip where they happen, a beat cut short leaves the world exactly as far along as the picture. The world's `shot` follows the beat's framing and a clip's cut (below); a cut the story does not allow, or one on the film's first clip, is dropped with a warning.
9. **Compile.** The compiler turns the clip into one flowing prompt (sound, the framing and the camera as a clause, who is on screen, who enters, the action, dialogue in quotes, the image the clip ends on). The first clip of a run carries the full `picture.style` and each character's full look, and opens on what the reference `shows`, because the renderer seeds that clip from the reference image; a character on screen that `shows` does not name enters the picture during it. Every later clip carries the blueprint's one-sentence `picture.anchor` (or the first sentence of the style), each character's `look_short` (or just the name) and props by name. An entity that enters the picture during the clip, because it was introduced in this segment (listed by the Director or not) or is on screen without having been in the previous clip's picture (the last event record's `on_screen`, plus what entered then), is described with its look in an "Entering the picture during this clip" sentence before the action and is never listed as already on screen, since the conditioning frames do not have it; the look is left out when the action already carries it verbatim. **Cuts.** Where the story allows them (`picture.perspective.cuts`, with `cutting` as its guidance), a clip may cut to a new shot: the Director names it in `cut_to` (the clip's first field, so the shot is decided before the action is written in it). The compiler opens such a clip on the shot the picture is in, then writes "The view cuts to …" with the camera clause before the action, LTX-2.5's convention for a cut in prose (6 of 6 written cuts rendered, no unwritten ones); the clips after it open on the new shot, and the next plan is told which shot the picture is in. A story without cuts (the Lego story today) is one continuous take, and its Director is told `cut_to` stays empty. Shorter anchors than the blueprint's let hair pieces and printed torsos in by clip 12, so `picture.anchor` and `look_short` keep their "bare"/"plain" words. Every clip has the shape selected for its beat (`src/i2v/shape.py`): the run's one shape, `clip_seconds` on the 8k+1 frame grid at the server's frame rate, which the Director is told, the event record and the story clock count in delivered seconds, the render request carries in frames and the player holds.
10. **Views and persistence.** A Showrunner run decided at the plan is spawned now, on the beat's first clip (step 7). The engine fills `current_beat`, `current_shot` and `current_dialogue`, which the runner, playback, history and the transcript read; the clip's action is the only prose. The event record (with its beat, intent and clip index) is appended and the world is saved to `logs/sessions/<session>/world.json` plus `events.jsonl`.

**Cut short.** When the viewer speaks while a beat still has unemitted clips, the live loop drops them, the next plan is told how the beat ended and on which image, and the Director writes the next beat from the line.

## World model tiers

| Tier | Where | Lifetime | In the Director prompt |
|---|---|---|---|
| Story bible | `stories/<story>/story.json` → system prompt | immutable | always (the film block: premise, question, engine, theme, tone, temperament, never; the truths; the picture; cast sheets with voices; locations) |
| World state | `WorldModel.entities` | current truth, mutated only by validated deltas | active entities in full, each with its `now:` state (a prop's says who has it); dormant props by id with `last_seen`; gone props by id |
| Cast notes | `Entity.notes` | durable facts from the Showrunner, characters only, at most `MAX_NOTES` (4) each, the oldest going first; a note that restates the cast sheet or a summary is not kept | in the world section (the system prompt stays byte-identical, so the API's prompt cache hits) |
| Scene context | `plan.scene`, last K clips | one scene | always |
| Open threads | `WorldModel.threads` | until paid off or pruned; nothing expires them in code | always, bounded, each with its age (segments and story seconds since it opened); the Showrunner decides continue, resolve or abandon for the stale ones, guided by the storyteller's temperament when it says how long setups run |
| Interventions | `WorldModel.interventions` | whole run | current input, deferred requests still owed, the last few handled |
| Event log | `WorldModel.events` / `events.jsonl` | append-only, one record per clip | only the last `recent_clips` verbatim |
| Summaries | `WorldModel.summaries`, `act_summary` | derived, rebuildable | the opening scene (pinned: the first compaction window) + act summary + recent scene summaries |

Entities carry `kind` (character, prop, location), `description` (for the writer: a character's `who`), `look` and `look_short` (verbatim for the renderer), `state` (where it is and how it is, in prose: a character's body, place in the frame and what it is doing; a prop's place, condition and who has it; replaced whole by the op that changes it), `location`, `present`, `gone`, `first_seen`/`last_seen` and `notes`, and characters also `voice`, `wants`, `nature`, `appears`/`appears_when` (a supporting character's entrance condition) and `dynamic` (introduced by the film). The world also records which characters the reference image shows (`opening_picture`), the picture before the first clip.

**Cast and perspective policy.** The blueprint names its protagonist (`cast.protagonist`, or the first character) with its starting state; the validator keeps it single and in the story, its look held in every clip. Supporting characters are written in the blueprint like any other, with an entrance (`appears`: must, should or may, and `appears_when`); they are registered from the start but not in the scene, the Showrunner decides when an entrance serves the story and the Director stages it with the character's id. `cast.newcomers` says what kind of characters the film may introduce beyond the cast (empty: none, and anything else that appears is a prop); a character the Director introduces is registered once with its look (and a short look for later clips), who it is, its voice and its state, and is listed in World now rather than on the cast sheet, so the cached system prompt never changes. `picture.perspective` gives the default (third-person, first-person, observer, …), the perspectives a beat may switch to and when; the Director sets `BeatPlan.perspective` on a beat that switches and the compiler writes a first-person beat as a point-of-view shot. The Lego story exercises all of it: Lego Man, the Spaceman (must appear, when a bit first fails badly), newcomers from any LEGO theme, and a first-person switch through binoculars.

## The player: watch and steer

The live loop (`run_live`) is a producer and a consumer on a bounded queue. The consumer hands rendered clips to a `Player` one at a time and the player holds each for its duration, so **the server is the clock**: the film advances at story pace whether or not anyone is watching, and a browser that joins late is told what is on air and seeks into it.

The producer renders **just in time**. Before playback starts it runs flat out to build the lead (`startup_clips` + 1 clips; that startup gate and the queue size are all `startup_clips` sets). Once the player has a clock, the render of the next clip is fired as late as it safely can be: the render estimate plus `buffer_seconds` before the clip is due on air, so every clip is queued about `buffer_seconds` before it plays (the steady-state buffer, 4.7 s); and the Director is asked for the next beat only when the current one has no clip left: at once, as soon as the beat's last clip has been emitted (`plan_early`), or with `plan_early: false` as late as the render allows. Until then, and while the next beat waits in hand for its fire, the producer listens for the viewer. A line that arrives cuts the beat in progress short (its unrendered clips are dropped), cancels a Director call in flight, and the Director writes the next beat from the line at once, so the line reaches the earliest clip that is not yet rendering: with the renderer under real time that is two clips after it was typed. A line that arrives after the Director has answered an earlier one but before that answer has played is joined to it, as a line that cancels a call is: the earlier line's recorded intervention is dropped and the pair is planned, recorded and answered once. A beat that answers a line has at most `answer_max_clips` (2) clips; the cap is stated in the user prompt's viewer section and enforced by the engine, since the answer call is the one on the critical path and its latency tracks its length. More slack absorbs slower renders and calls; less slack lets a line land sooner.

**Failures.** The previous clip's render is known before the next clip is emitted (it lands about 1.2 s before that clip's fire in steady state, so nothing waits). A failed render is retried once when the retry can still land before its clip is due (the p95 of the last 20 renders plus a margin); otherwise, or when the retry fails, the engine restores the world and the beat from a snapshot taken before the clip was applied (re-applying any Showrunner update that landed since), cuts the beat, tells the next plan that the clip never reached the viewer and that the picture ends on the clip before, and the segment is replanned under the same number; a viewer line whose answer was on that clip is answered again. An exception while emitting a clip takes the same route. Three failed segments in a row stop the film rather than loop on a renderer that is down. Every step is in the timing log (`render_done` with its attempt, `render_retry`, `rollback`, `line_requeued`, `emit_failed`) and the transcript. `fail_soft: false` skips a failed render instead.

`WebPlayer` (`src/web/`) is an aiohttp server: `/` serves a single-page player, `/events` is a server-sent-events stream (`hello` with the history, `queued` for prefetch, `playing`, `input`, `status`, `ended`), `/input` takes a typed line at any moment, `/clips/N.mp4` serves the clip for segment N with Range support, and `/beacon` takes the page's own timing (see below). The page plays clips back to back and joins them by the config's `seam`: `fade` stacks two video elements and crossfades picture and sound for 250 ms at each seam; `overlap` (the live config) renders each clip's 9-frame window on top of its 144 new frames (153 in the file, 6.0 s held), keeps a pool of three elements, cuts the picture when the outgoing clip reaches its last new frame (the next clip opens on the same frames) and crossfades the sound over the 0.375-s overlap, bringing a clip with speech in at once; the server then keeps each clip under `audio_ceiling_lufs` (-18) with its audio padded to the video, a value `vast_run.sh` passes from the same config and the client compares with `/health`. In a live film the overlap seam showed no duplicate frames and no luminance dip. The page holds the last frame while the next clip is late, shows the clip's lines as a caption, and keeps a script column where each clip appears with its beat, the viewer's line and the Director's disposition (absorbed / deferred / declined, with the reason).

**Timing log.** Every run writes `logs/sessions/<session>/timing.jsonl` (`src/util/timing_log.py`), one JSON line per event, each with a monotonic `t` and a Unix `wall`: `session_start` (code revision, config, clip length), per clip `emit`, `fire` (with how long until it is due on air), `render_done` (render wall and the server's `X-*` headers), `enqueued` (with the margin before air), `playing` (with how long the consumer waited: a stall) and `hold_end`; per viewer line `line_received` (id, the clip on air and how far into it), `line_taken`, `line_landed` or `line_dropped`; per Director call `director_start` and `director_end` (clips, the Director-only time, re-ask, fallback, cancelled); and the page's `beacon`s (`swap`, `loadstart_on_playing`, `waiting`). Nothing reads it during a run; it is the record to check a run against afterwards (stalls, queue margins, render times, how long a line took to reach the screen).

Without a video backend the same page plays the film as text: each clip is held for its planned duration and shows its action, so a headless config gives a working session and the loop and the input path are exercised offline. `configs/director.replay.yaml` uses the `replay` i2v backend, which serves clips left by an earlier live run, to develop the player with real video and no GPU. `TerminalPlayer` keeps the original ffplay window and stdin reader behind the same interface.

## Viewer influence

Input is absorbed at the lowest level that fits. The Director classifies each request as `absorbed` (it happens now), `deferred` (it needs setup; the reason is recorded and the request stays visible as owed), or `declined` (only when it breaks the rules of the world). A later beat can deliver a deferred request without new input: it names the request by the segment it was made at (`delivered_request`, the number the viewer section lists), and the validator resolves exactly that one; with a single request owed an absorbed beat that names none still resolves it, with two or more nothing is guessed. The Showrunner sees the whole intervention list and is told to make room for deferred requests in the next scene. Structural rule checks (cast lock, entity existence, who may speak) are the validator's; judgment calls stay with the Director, which is told to bend toward the spirit of a request rather than refuse. A line never waits for a beat to end: it interrupts.

## Speech

There is no narrator. Every spoken word is a character's line: any character in the film may speak (there is no `speaks` flag), and the Director decides beat by beat whether a moment is served by a line or by silence. A clip's `dialogue` is a list of lines, each with a speaker, the line and a delivery; the validator drops a line whose speaker is not a character, and a newcomer may speak in the clip it enters. Characters carry a `voice` in the blueprint (a description, language, accent and default delivery; a newcomer gets the Director's few words), which the world keeps and the compiler uses in LTX-2's single-speaker form: `Name says in a {delivery} voice, "line"`, followed by the language and accent when given. LTX-2.5 renders the lines natively with the clip's sound; nothing is mixed in afterwards. The event log, the recent clips, the transcript and the player all carry the lines (`Name: line`). Unverified on the GPU: two speakers in one clip, and whether the model animates a minifigure's printed face while it speaks.

## The video boundary

The renderer receives a compiled prompt, the clip's shape (its frame count) and a seed derived from the run's seed key (the session id unless `ltxv_seed_key` names another run) and the segment, so a rerun under the same key reproduces the noise. The reference image (`picture.reference`: the image and what it `shows`) is checked twice: when the story loads (it exists and decodes; `shows` may be blank, and a story may have none, though a video run refuses to start without one) and when a run starts, against the server's render size: under `i2v_reference_fit: pad` (the default) a reference within 5 % of the render aspect is cover-resized and one outside it letterboxed with a warning (and a second warning when its border is too uneven for the fill to continue it); under `strict` (the live config: one standard size for render and reference) only a reference at the render aspect to the pixel is taken, resized whole with no crop and no padding, and any other refuses to start. The verdict is the timing log's `reference` record. Every clip is conditioned on the previous clip's tail (the server's sliding window); the first clip of a run is seeded from the reference image instead, and the compiler opens that clip on what the reference `shows`. After a server restart the client sends the last clip's last nine frames with the reference (`ltxv_restart_recovery: "window"`, the default), and the restarted server continues the picture; only when that tail cannot be read is the clip re-seeded from the reference, and the next Director call is told the picture was reset. Nothing re-seeds mid-film: every clip is conditioned on the one before it, a prose cut where the story allows one (above) included; otherwise a change of angle or distance is a camera move inside a clip. Re-seeding from the reference would reset costume, props and position to the reference's state. Only the compiler knows the model's dialect; the schemas do not change when the model does.

## Configuration

```yaml
graph: "director"
clip_seconds: 6                # the run's clip shape: 145 frames at 24 fps (153 with the overlap seam), 6 s on air
startup_clips: 1               # clips queued before playback starts (startup only)
buffer_seconds: 4.7            # steady state: each clip is ready about this long before it plays
fail_soft: true                # a failed render is retried or rolled back and replanned; false = skipped
answer_max_clips: 2            # a beat that answers a viewer line has at most this many clips
recent_clips: 6                # verbatim clips in the Director prompt
max_clips_per_beat: 4          # the Director plans one beat of up to this many clips per call
scene_seconds: 240             # about how long a scene runs; the plan shows both roles the running time against it
compaction_interval: 10        # Showrunner compaction cadence, in segments
showrunner_min_gap: 4          # fewest segments between two Showrunner runs
director_model: ""             # optional per-role model overrides
showrunner_model: ""
director_service_tier: ""      # OpenAI processing tier for the Director call ("priority": ~2.5x the tokens/s)
ltxv_negative_prompt: ""       # "" → the server's default; the distilled recipe never encodes it (guidance 1.0)
ltxv_seed_key: ""              # render seeds derive from this key and the segment; "" = the session id
```

`configs/director.yaml` is the headless config; `configs/director.live.yaml` drives LTX-2.5. The blueprint (`stories/<story>/story.json`, with the story's reference image beside it) carries the story: what the film is (`premise`, `question`, `engine`, `opening`, `truths`), who tells it (`storyteller`), who is in it (`locations`, `cast`, each character's `look` and `look_short`) and how it looks (`picture`: `style`, a one-sentence `anchor`, the `reference`, the `perspective`). Everything in `src/prompts/`, the schemas, the compiler and the engine is story-agnostic.

## Testing

`pytest` runs the offline suite on the mock LLM (`llm_backend: "mock"`), in a few seconds and without an API key: `tests/test_story.py` (the world model, the validator and the cast policy, the compiler, persistence, and that every blueprint field is in the field guide), `tests/test_engine.py` (the film loop end to end: beats emitted clip by clip, a viewer line cutting a beat short, the re-ask path, the non-blocking Showrunner, a failed render rolled back and replanned, a line whose answer failed answered at the next plan), `tests/test_render.py` (the clip shape every consumer reads and the server must have warmed, and the strict reference fit) and `tests/test_web.py` (the live loop through the web player over HTTP, in text mode and with replayed clips).

## Not built yet, by design

Per-character reference images and keyframe conditioning from the current look; semantic retrieval over the event log; character knowledge and relationship graphs; a cinematic-language rewriter; multi-viewer input aggregation.

Resuming a run is not built: every run starts a fresh world in its own session directory, and the `world.json` and `events.jsonl` written there are for inspection. No multi-location story has run: the validator's location resolver (ids, names, prefixed forms such as "at the_white_void", then the first location id contained in the text) has a known gap: in the fallback a location whose id is a prefix of another's wins. Test it on a two-location blueprint before the first one runs.
